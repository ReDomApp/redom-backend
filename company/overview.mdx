AUREVON GROUP, INC. maintains a portfolio of software products and engineering systems. This page explains how the portfolio is represented in the master repository and how the separate documentation repository records the verified implementation.

## Repository ownership and documentation flow

- **Master engineering source:** [ReDomApp/redom-backend](https://github.com/ReDomApp/redom-backend), branch `main`.
- **Documentation destination:** [ReDomApp/docs](https://github.com/ReDomApp/docs), branch `main`.
- **Documentation platform:** Mintlify deployment `aurevon-group-inc`.

The master repository is a pnpm monorepo. Its `artifacts/` directory contains multiple product applications, backend services, workers, and supporting systems. The `lib/` directory contains shared libraries. The separate `docs` repository is the publication destination, not the implementation source.

## How to interpret implementation status

Documentation distinguishes four states:

- **Implemented in source:** behavior or interfaces are present in the current `main` branch.
- **Configured for runtime:** code supports a capability, but live credentials, infrastructure, or provider provisioning may still be required.
- **Planned or incomplete:** source documentation explicitly identifies a future capability or an unfinished integration.
- **Not independently verified:** source code alone cannot prove that a deployed service, provider account, DNS record, or production workflow is operational.

A route or worker in source is not, by itself, proof of production availability.

## Documentation authority

For current implementation details, use this order:

1. Current explicit product and security requirements.
2. Current source and configuration on the master repository's `main` branch.
3. Current tests and verification results.
4. Live provider, database, and deployment state when operational status is relevant.
5. Historical engineering notes as context, not as current authority.

Never copy credentials, private keys, tokens, customer data, or sensitive runtime values into public documentation.

## Documentation boundaries

The documentation project may inspect the master repository and update this documentation repository. It must not modify product source, deploy services, change production databases, or operate provider accounts as part of documentation generation.
