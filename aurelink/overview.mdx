Aurelink provides number-based services such as short-term SMS activations, longer-term rentals, and related account workflows. Its executable TypeScript routes and services are mounted inside the existing ReDom backend rather than running as a separate API server in this repository snapshot.

## Product surfaces

The workspace contains:

- `artifacts/aurelink`: integration documentation and tests.
- `artifacts/aurelink-public`: standalone public login experience.
- `artifacts/aurelink-admin`: private operations frontend.
- `artifacts/redom-backend/src/routes/aurelink*.routes.ts`: backend route modules.
- `artifacts/redom-backend/src/services/aurelink`: provider clients, pricing, wallet, renewal, and lifecycle services.
- `artifacts/redom-backend/src/middleware/aurelink-auth.middleware.ts`: Aurelink-specific authentication middleware.

The public and admin frontends are separate from one another. The admin README explicitly states that the private admin tool is not customer-facing and must not be given public signup or payment flows.

## Provider boundaries documented in source

The Aurelink integration README describes two number-provider roles:

- **SMSPool:** short-term activation inventory and SMS polling.
- **NonVoip:** long-term and dedicated number features.

Aurelink also uses a line-type verification service in the documented purchase flow. The current README says that a number must positively classify as a valid mobile line; a missing or failed lookup fails closed.

Provider credentials are server-side configuration and must never be placed in client applications or documentation.

## Main customer workflows

### Short-term activation

The documented flow is:

1. Read live service, country, pool, price, and stock catalog data.
2. Request a short-lived, single-use quote.
3. Complete hosted checkout or use the supported wallet path.
4. Redeem the quote only after the backend verifies the corresponding paid transaction or wallet debit.
5. Poll the activation's message endpoint until the activation completes, expires, or is cancelled.
6. Process cancellation and any wallet credit only after provider confirmation.

The integration README documents a 10-minute single-use activation quote and SMS polling rather than a push webhook for temporary activations.

### Long-term rentals

The rental flow obtains a live quote for a rental and duration, gates purchase on payment, and exposes status, message, renewal, and cancellation operations. Renewal is payment-gated.

### Wallet

The backend exposes wallet balance and ledger reads, plus wallet top-up through hosted Stripe Checkout. Wallet-funded purchases use server-side debits and ledger records. Provider-confirmed cancellation/refund is required before a corresponding wallet credit is treated as final.

## Documented API surface

The integration README lists these route families under both `/aurelink/*` and `/redom-backend/aurelink/*`:

| Area | Routes documented in the integration README |
|---|---|
| Status and catalog | `GET /status`, `GET /catalog/services`, `GET /catalog/countries`, `GET /catalog/pools`, pricing, stock, suggested countries, success rates, valid pools, rental catalog |
| Activation | `POST /quotes`, `POST /checkout`, `POST /activations`, activation message polling, resend, cancellation, order history |
| Rentals | rental quotes, checkout, purchase, messages, status, renewal, cancellation |
| Wallet | `GET /wallet`, `GET /wallet/ledger`, `POST /wallet/topup` |
| Additional capabilities | administrator carrier lookup and selected eSIM plan/profile reads |

The integration README is a useful endpoint inventory. Exact authentication, request schemas, status codes, and current route behavior must be checked in the route implementation before publishing a customer-facing API reference.

## Billing and safety rules

- Customer prices are calculated server-side from live provider prices and product-specific rules.
- A quote is short-lived and single-use.
- Purchase fulfillment requires authoritative payment or wallet verification.
- A client must not report a successful purchase based only on a redirect or client-side callback.
- Unknown or failed line-type checks fail closed.
- A provider cancellation response is not automatically a refund confirmation.
- Admin-only operations remain protected and are not exposed as ordinary customer actions.

## Implementation status caveat

A route or service being present in source does not prove provider inventory, credentials, payment processing, or live carrier classification is operational. Check the current deployment and provider state before describing any market, country, service, or number type as available.
