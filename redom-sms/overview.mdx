ReDom SMS is documented as a ReDom-owned SMS infrastructure layer. It is intentionally independent from the existing ReDom backend until its software and carrier connectivity have been completed and validated.

## Source location

- Service: `artifacts/redom-sms`
- API reference: `artifacts/redom-sms/API.md`
- Transmission layer: `artifacts/redom-sms/src/transmission.ts`

## Service responsibilities

The service owns the application-level SMS lifecycle:

- API authentication and E.164 number validation.
- GSM-7 and UCS-2 encoding selection.
- Multipart segmentation.
- Durable message persistence and queueing.
- Idempotency and retries.
- Delivery receipts and message state.
- Inbound messages.
- Destination routing and carrier adapter boundary.
- Opt-out state and webhook delivery.

The README describes PostgreSQL-backed durable queue processing and a direct SMPP/SMSC transport. It supports carrier route selection and failover where routes are configured.

## Network connectivity is an external dependency

An internet server and SMPP implementation do not independently create access to public mobile networks. Real delivery requires lawful carrier or SMSC interconnection, issued credentials, permitted sender addresses, throughput limits, delivery-receipt behavior, inbound permissions, and any required country-specific registrations.

The software intentionally keeps the carrier/SMSC connection behind an adapter contract. No consumer SMS API provider is required by the documented architecture.

## API surface

The service API document defines a `/v1` base path and bearer API-key authentication. Documented operations include:

- `POST /messages` and `POST /messages/batch` to submit messages.
- `GET /messages` and `GET /messages/:id` to inspect messages.
- `POST /messages/:id/cancel` to cancel queued or scheduled messages.
- Webhook endpoint management.
- Inbound message acceptance from an authorized SMSC/carrier gateway.
- Opt-out creation and removal.

Webhook events include queued, submitted, delivered, failed, expired, cancelled, received, and opted-out message events. Webhook requests use an HMAC-SHA256 signature over the exact request body.

## Message lifecycle safety

- Duplicate idempotency keys must not create duplicate messages.
- A message is not delivered merely because it was accepted by the HTTP API.
- Carrier acceptance and final delivery receipts are distinct states.
- Cancellation is only available while a message is queued or scheduled; carrier acceptance cannot guarantee network cancellation.
- Opt-out keywords documented by the API include STOP, UNSUBSCRIBE, CANCEL, END, and QUIT.
- The send API rejects opted-out recipients unless an authorized compliance workflow explicitly overrides the check.

## Production phases

The README lists these phases: validate and build the software layer, deploy isolated infrastructure, establish lawful carrier/SMSC interconnection, prove mobile-terminated delivery plus delivery receipts and mobile-originated inbound SMS, then add routes and integrate with the ReDom backend.

Until carrier connectivity and real-world delivery tests are verified, describe ReDom SMS as software infrastructure under development rather than a globally connected live carrier network.
